## Goals / Non-Goals

**Goals:**

- In scope：可理解的 edit／stop／remove 分類、明確後繼世代、限定矩陣的新布局／目的地轉換、停止與移除後的歷史查閱。

**Non-Goals:**

## Decisions

### 操作分類與停止移除

名稱、週期與同布局來源選擇保存為同一 group 的新 draft revision；語意／成員／目的地影響必須重做相依 proof，舊 applied snapshot 不變。布局、固定儲存身分或已移除設定改走後繼流程。採 server `actions[]`：`action`, `allowed`, `reason_code`, `next_action`, `requires_review`；前端不根據按鈕名稱猜測。

「停止新記錄」只停止新 intake，既有 accepted samples／outbox 仍交付原目的地。「移除記錄設定」保留 tombstone、immutable versions、收據、schema operations 與 unresolved operations。停止必須可在 live connector 已變更／不存在時使用自身 saved revision；移除仍需 ownership guard 與既有 scope/CAS，失敗顯示停用替代路徑，不自動繞過。

拒絕把 disable 等同 drain/cancel，或以 DELETE 表示外部 SQL 資料刪除。

### 後繼世代與唯一擁有權

邏輯 identity 是既有 workspace／device-circuit／profile／canonical-role key，補上 persisted lineage ID 與遞增 generation。新世代使用新的 group ID；舊 group ID、applied versions、SQL receipt identity 永不復用。canonical key 保留，世代關聯保存 predecessor/successor；只有經審核並排程的 transition 能更新 key 的 current／pending head，不能以普通 ensure 取代 deleted head。

後繼準備階段只建立不接受資料的 reserved draft。允許的重疊僅限同 lineage 的 predecessor 與該 operation 保留的 successor；其他同來源／同 profile owner 仍拒絕。CAS 同時綁 workspace、predecessor/current head、群組 revision、connector revision 與 operation ID；重送相同 request 回同世代，不同 intent 衝突。

移除後的重新建立從明確 `recreate` review 開始，產生新 generation，不 revive tombstone、不刪 key。舊 backlog 未清空不是自動丟棄理由；有 frozen owner proof 才可繼續。已 finalized effect／outbox／receipt 永遠留原 owner；尚未 finalized 的觀測依既有 cutover engine 的 persisted fence 與 observed_at 契約，可原子 durable handoff 至新 consuming owner，保留原 acceptance provenance、binding proof 與移交 audit，不刪樣本、不雙計。停止後恢復相同設定優先重新審核同群組，不額外產生世代。

### 能力限定的轉換矩陣

| 來源 → 目標 | 本批支援條件 | 明確限制 |
| --- | --- | --- |
| managed_wide_profile_v1/plain → managed_long_v1/plain | SQLite 或 PostgreSQL；同引擎、完整群組來源、同 profile kind 與語意 | 不把 latest 改 mean、不改 counter binding |
| managed_long_v1/plain → managed_wide_profile_v1/plain | SQLite 或 PostgreSQL；所有來源型別／role 有 wide 等價表示且 schema proof 通過 | 不支援的 exact source shape 逐項阻擋，不截斷或強轉 |
| managed layout → 同 layout、同 mode 的另一目的地 | 同引擎；SQLite／PostgreSQL；MySQL／SQL Server 僅 verified managed long | 新 connector／storage scope 全部重新 probe、preview、confirm；不復用舊 proof |
| 已移除 managed 設定 → 同配置或上列允許目標 | 同邏輯 identity 的明確新 generation，重新準備 | 不把普通 ensure 重試解讀成 recreate |
| legacy wide/custom → long | 保持既有 API 契約及能力門檻 | 既有邊界 correctness 由相依 change 交付 |
| 其他組合 | 不支援，回 typed reason | 包含 MySQL／SQL Server wide、跨引擎、plain↔Timescale/native_monthly、partial-source 新 successor |

轉換寫入新資料表 generation／經確認的新 storage owner；不在原表更改 layout、不覆寫原 generation 的 schema proof。名稱由 backend 驗證與 quoting，不由 UI 拼 SQL。Timescale／native_monthly 的同 mode 目的地換接仍需能力證據；不符合則阻擋，不降級成 plain。

### 審核邊界與復原

擴充既有 write-group 路由，提供唯讀 `GET .../write-groups/:id/lifecycle`、`POST .../:id/successor-review` 與確認 `POST .../:id/successor`；operation readback 沿用既有 ledger 模式。review 回傳 `transition_id`, `lineage_id`, `from_generation`, `to_generation`, `source/target`, `moved_sources`, `boundary`, `pending_by_revision`, `blockers`, `digest`。確認必須送 reviewed digest 及所有 expected revisions；失效回 typed conflict，無變更。

review、保存 draft、schema apply、開始新 intake 與 SQL committed 分別呈現。pending_by_revision 分開 samples、outbox 與 blocked/unknown 狀態，不把單位不同的值相加成「筆數」。所有權時間明確使用 source observed_at，而非 received_at、accepted_at、ACK 或 reconcile 時間：observed_at < boundary 屬舊 owner，observed_at >= boundary 屬新 owner。延遲 reconcile、事先已接受但 observed_at 跨界的觀測，以及晚到但尚未 finalized 的樣本，均沿 `fix-recording-cutover-boundaries` 唯一 boundary engine 的 persisted accept/closure fence、durable handoff 及 lateness 契約處理；已 finalized／凍結的 effect、outbox、receipt 不重算、不重導。新 successor 的累積 profile 以第一筆邊界後有效樣本建立 baseline，該筆 delta 為 NULL；相同 frozen binding／epoch 證據不代表自動承接舊 baseline，也不補造跨 gap 用量。

結果未知時保留同 operation/transition ID，查狀態後才能重送完全相同 intent；切頁、改名、重整不產生新世代或隱藏 unresolved operation。取消未提交 review 無副作用；已確認的 scheduled transition 不提供含糊取消，rollback 必須另做前向 review。

#### task 2.2：後繼世代與唯一擁有權的儲存實作

本節記錄既有 task 2.2 的實作決策，不新增需求、任務或相依關係；範圍僅限內部 SQLite 設定資料庫的 expand migration，不操作外部 SQL 資料、不要求外部資料庫環境。

- `write_group_lineages` 是 current／reserved head 的唯一 authority，保存 workspace、獨立 lineage CAS revision 及成組有效的 reservation operation／intent；`write_group_generations` 只保存 group、lineage、遞增 generation 與 predecessor 的歷史成員關係。兩表不複製 WriteGroup 設定、目的地、schema proof、applied snapshot 或 receipt。lineage ID 使用 `common.NewUUID`，不借用 group ID／revision 的序列；migrator 不依賴 workspace package。
- `write_group_basic_keys` 與 `write_group_profile_keys` 的既有欄位、tuple key、索引、約束及時間戳維持原值；`group_id` 永久保留為 generation 1 的 genesis anchor，不改成可變 head。兩表新增 nullable `lineage_id` reference，兼作持久 migration marker；nullable 僅供 expand 過程使用，完成初始化後 NULL／空 reference 一律無效。
- 初始化按既有 key 指向的 distinct group 建立一條 lineage；同一 group 的 basic／profile aliases 共用它，tombstone 仍初始化，沒有 key 的 legacy group 不補造 lineage。每條初始 lineage 的 current 是原 group、revision 是 1、reservation 全為 NULL，generation 1 沒有 predecessor；所有原始 key、群組、immutable versions、accepted payload、outbox、receipt 與歷史保持不變。
- canonical lookup 先讀實際 key row，再於同一 read transaction 驗證 reference／scope 並解析 current head；只有 key 確實不存在才回 `ErrWriteGroupNotFound`。key 存在但 metadata／head 缺漏或矛盾時回 `ErrWriteGroupLineageCorrupt`，不得包裹 NotFound 或落入 create。historical lookup 則由指定 group 的 generation／lineage 回到 genesis key，保留該歷史 group 的 generation／predecessor，不把 key anchor 移到新 head。
- migration 狀態由兩個 `lineage_id` 欄位及兩張 registry 表這四項設計構件共同判定：全部不存在才首次初始化；全部存在只驗證；任何混合狀態 fail closed。`ensureSQLiteWriteGroupsTables` 在舊 helper 可能補建 key table 前先檢查，並在取得 SQLite write lock 的 migration transaction 中重新判定；DDL、distinct-group backfill、alias references 與完整驗證同一交易 commit，任一步失敗一併 rollback，不用逐 statement migration helper 分拆。
- reopen 不補資料、不重設 head／revision、不盲目修復。驗證拒絕缺漏／NULL／空 key reference、缺失 group／generation／lineage、workspace 或 alias 矛盾、無效 genesis、跨 lineage 的 current／reserved head、不完整 reservation tuple，以及非同 lineage 或非 generation n−1 的 predecessor；有效的後續 generation、current head 與 reservation 原樣保留，不要求它們仍等於初始狀態。
- fresh canonical create 在既有 transaction 內先插入 group，再初始化 lineage／generation，最後以明確 `lineage_id` 插入 key；同 group 的第二個 alias 重用已驗證 mapping。既有 key／lineage reference 的 metadata 缺漏不是 fresh create，不得藉初始化修復；read／replay 不呼叫 initializer。失敗時 group、key 與新增 metadata 一起 rollback。
- 普通 ensure 仍拒絕 tombstone；task 2.2 不 reserve successor、不移動 head、不啟用 intake，也不放寬 ownership。後續 task 的明確 review、operation identity、CAS、scope／revision、capability 與既有 live-transition 前置驗收 gates 全部保留；測試可 seed 後續世代驗證讀取／重開，但不新增 live successor 路徑。

#### task 2.3：recreate reserved draft 的內部保留契約

本節釐清既有 task 2.3 的 common／managed-profile 機制，以及使用者已同意的 Basic-only 原格式、完整原來源重建；不擴充「能力限定的轉換矩陣」，也不宣稱任務完成。In scope 是 tombstoned canonical current head 的私有 backend reservation；非 deleted head 不進入此 primitive。Out of scope 是 current-head transfer、applied version、runtime／intake、ownership fence、外部 DDL、公開 successor routes 與前端；上述後續能力仍依原任務及驗收 gates 交付。

- 私有 `reserveRecreatedDraft` 接受 workspace／lineage／predecessor identity、expected workspace／lineage／predecessor／saved source connector／target connector revisions、operation ID 與完整 target intent；回傳新 draft、lineage／generation、predecessor、operation／intent digest 及一致的 workspace revision。不得擴充公開 mutation DTO、讓 caller 提供可信 digest 或提供 ownership bypass。
- backend 先正規化 frozen request，排除新 group ID、server-owned revision／status／時間戳與 schema proof 等衍生欄位，再以完整 scope、原 expected revisions、operation 與 target intent 計算 deterministic digest；不依可變 live state 或新表名生成 digest。同 operation 改名、設定、目的地、來源或 CAS 都是不同 intent；pending 時不同 operation 即使 target 相同也回 typed conflict。
- 先以 coherent read 驗證並回放完全相同的 pending reservation，再檢查新 mutation 的 CAS。純 replay 不重新檢查 live target／capability，不因初次 commit 或無關 workspace 修改造成 revision 前進而另建世代；返回原 reserved group／generation，不寫入、不授權 stale connector 的新 mutation。reservation／generation／predecessor linkage、draft status 或 empty applied revision 矛盾時 fail closed，保留 `ErrWriteGroupLineageCorrupt`，不得改成 NotFound 或自動修復。
- 新 reservation 在既有 workspace transaction 內重新驗證完整 scope／CAS、deleted current head、backend-resolved source／target evidence 與既有 backlog ownership guard；managed-profile 分支沿用 `ValidateWriteGroupTransitionStructure`，不得推定缺少的 engine/type/capability evidence。新 group 與 members、current generation 的下一世代、唯一 lineage reservation、local storage scope 與 workspace compatibility projection 原子 commit；失敗全部 rollback，不留下 orphan 或部分 revision 更新。
- `write_group_lineages` 仍是唯一 current／reserved authority；保留 current head 與全部 genesis aliases，只 CAS 寫入該 lineage 的 reserved group／operation／digest 並遞增 lineage revision。successor 不插入第二個 canonical key、不重設 key 時間戳、不復用 ID／generation，也不新增 generic owner exemption；ordinary ensure 仍解析原 tombstone 並拒絕。歷史 group、versions、accepted payload、outbox、receipts 與既有 operations 原樣保留。
- reserved draft 始終不接受資料且無 applied revision。普通 Update／rename／Delete／Disable、Apply、schema preview／confirm／apply、recording-start 與舊 cutover target activation 不得修改或啟用它；在外部 probe／DDL 或 mutation 前以 typed `successor_reserved` reason 阻擋，readiness／actions 同步 unavailable。Get／List、tombstone／version 查閱、既有 accepted delivery 與 operation readback 保持可用，不因防護隱藏 pending 結果。
- 先用失敗測試證明 competing CAS、相同／不同 frozen intent，再驗證跨連線競爭只有一個 reservation；group／generation／reservation／projection 任一步失敗均完整 rollback，lost commit acknowledgement 與 restart 回到原 pending 結果。回放不得繞過儲存 metadata 驗證；無法讀回完全相同 durable result 時保留原 typed conflict/error。這是 pending reservation 的 idempotency，不是永久 operation ledger；tuple 日後清除後的結果保存／讀回仍由 task 3.6 負責，不能以最新 head 或 operation 冒充原結果。
- **已確認的 Basic-only 同配置重建**：取代本節原「待使用者確認」的暫停決定；使用者已同意 tombstoned、具有 canonical Basic key、`RecordingProfile == nil` 的 `managed_wide_v1`，僅在既有 SQLite／PostgreSQL plain wide 契約內沿原格式、完整原設備／來源與記錄語意重建。這是 stable lineage 的同配置 recreate，不是新增型態互轉；managed-profile 仍走 task 1.2 的 `ValidateWriteGroupTransitionStructure`，legacy wide/custom-to-long 仍走原契約及 guards。
- Basic-only successor 必須保留 canonical device／role、完整 device／point／tag source set、source／mapping evidence、member meaning、measurement binding、週期、reduction、row／write policy、layout 與 plain mode。已有 applied revision 時，以 scope 正確的 immutable applied definition 作為來源語意基準，current tombstone revision 仍供 CAS；未套用 draft 不得把改變的來源／記錄語意包裝成「原樣」。保留既有 exact-source guards；基準或 engine／type／binding evidence 缺失、變動或不相容時回 typed refusal，不推定、不自動轉換。
- Basic-only 同樣只保留新 group ID／下一 generation 的 non-accepting draft；原 key／current head／tombstone／versions／accepted data／outbox／receipts／operations 不動。新世代使用新 owned table／storage identity，不複用原實體 owner 或 schema proof；task 2.3 不執行外部 DDL，後續必須完成 fresh review、schema preparation／confirmation 及既有 readiness／live-transition gates 才能 intake，不搬移或改寫歷史 SQL。

## Risks / Trade-offs

- [新世代可能被當成第二個 writer] → 在 canonical key 的 CAS reservation 與 effective boundary 同一交易處理，其他 create/apply 路徑不放寬 owner check。
- [停止後仍見 SQL 寫入造成誤解] → 清楚展示「不再接受新資料／正在補送舊資料」及原 revision；不承諾 stop 等於取消交付。
- [累積計數跨世代重設或重算] → 對等語意保留 frozen binding，但新世代 baseline 不沿用舊世代；第一筆有效邊界後樣本 delta 為 NULL，拒絕跨 gap 虛構用量，依相依 change 的 epoch/boundary 測試驗收。
- [外部 DDL 與內部交易不同步] → 使用準備／確認／ledger readback，後繼尚未 ready 前舊 owner 不停止。

## Migration Plan

Expand：增加 lineage／generation／pending transition metadata，既有群組按原 key 與 group ID 初始化第一世代，無 SQL 資料變動。Migrate：逐種轉換矩陣經 disposable DB 測試後啟用，同時保留既有 API compatibility。Contract：只移除已遷移的重複 UI 判斷，不刪歷史 key／versions。回退採停用新入口並保留 ledger，新世代已接受資料時不得還原資料庫 metadata；需要回原設定則另做前向轉換。

本節落實既有中斷復原／移除後重建契約，補齊先前明列的 never-applied G1 缺口；不擴大轉換矩陣，不新增資料表、一般工作流程引擎、scheduler、歷史回填或操作搜尋產品。
