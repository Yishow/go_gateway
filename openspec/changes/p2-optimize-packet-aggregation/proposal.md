# p2-optimize-packet-aggregation

## 摘要

本提案建議實作**智能封包聚合 (Smart Packet Aggregation)** 機制，在 Runtime 動態分析並合併相鄰的暫存器讀取請求，以最小化網路封包交互次數 (RTT) 並最大化資料吞吐量。

## 動機

在目前的實作中，使用者若配置了 `D100` 和 `D102` 兩個 Tag，系統會發送兩次 Modbus 請求。然而，根據 HslCommunication 的效能建議，最佳做法是發送一次 `Read D100 Length 3` 的請求，然後在記憶體中拆解數據。

對於擁有數千個 Tag 的大型專案，這種「逐點讀取」的方式會導致：

1.  **網路壅塞**：大量的小封包佔用頻寬與 switch 資源。
2.  **掃描週期過長**：每個請求的 RTT 累積，導致無法滿足 100ms 等高速採集需求。
3.  **設備負載過高**：頻繁的連線請求可能導致老舊 PLC 處理不過來。

## 範圍

- **模組**：`internal/datalink`, `internal/protocol`
- **能力**：`protocol-connectors` (增強), `collection-optimizer` (新增)

## 預期效益

- **輸送量提升**：對於離散位址配置，預期可減少 50% - 90% 的網路請求次數。
- **配置簡化**：使用者無需手動計算優化區塊，可隨意定義 Tag。
- **即時性增強**：大幅縮短整體掃描週期 (Scan Cycle Time)。

## 風險與考量

- **協議限制**：需嚴格遵守各協議的 PDU 限制（如 Modbus PDU 最大 253 bytes）。
- **跨區塊問題**：需正確處理記憶體區塊邊界（如不能將 D 區與 M 區合併）。
- **寫入一致性**：聚合通常僅適用於「讀取」，寫入建議維持單獨指令以確保安全性。

## 測試策略 (TDD)

本變更採用 **TDD** 流程，透過測試案例驅動聚合演算法的實作：

1.  **演算法單元測試**：提供多組 `[]Point` 輸入（包含連續、分散、空洞、跨 PDU 等場景），斷言 `BlockMerger` 的輸出是否符合預期。
2.  **資料映射測試**：驗證 `Dispatcher` 能否從聚合後的 `Block` 數據流中，精準提取出每個 Point 對應的數值，確保 Byte Offset 計算無誤。
3.  **基準測試 (Benchmark)**：在 CI 流程中加入 Benchmark，確保優化演算法本身的執行時間維持在微秒級別，不成為新的瓶頸。
